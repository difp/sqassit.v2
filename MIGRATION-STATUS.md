# Migration status

Reference: SQASSIT `736a779f59d9e13d7e3a0f0401d6dd1c642cfada`, imported under `legacy/`.

## Implemented in Rust

- Telegram Mini App initData and scoped token validation, with fixed vectors generated by the reference implementation.
- Stable anonymous identities and an in-memory sliding-window rate limiter.
- SQLite schema initialization and legacy column migrations, including notification expiry and onboarding backfills. SQLite uses WAL, a busy timeout, foreign keys, and the `search_norm` function.
- Atomic training booking, approval, rejection, cancellation and FIFO promotion, including simultaneous requests for the last place.
- Match creation and privacy-aware listing are available; creation atomically enrolls the organizer. Match attendance endpoints implement authenticated joining, leaving, approval and rejection with manager/coauthor checks, phone cutoff, rate limits and atomic FIFO promotion, including concurrent requests for the last place. Tournament room access is restricted to booked players and managers; only the organizer can delete a match or modify coauthors. As in the Python API, the coauthor list discloses their real identity to authenticated users; this behavior needs a privacy review. Match notifications are mock-tested and compared for joining, leaving, requests, decisions, promotion, deletion, creation and feed publication; live delivery, ordering under simultaneous events and restart recovery remain unverified.
- Authenticated profile read/edit, privacy-aware public player profiles, iCalendar export, onboarding acknowledgement, notification settings, the player-facing training schedule, booking and cancellation use SQLite and Telegram initData. Schedule participant and coach data are loaded in batches, with multi-training privacy and status coverage; synthetic benchmarks cover 50,000-player search and a 2,000-training/12,000-booking schedule, but production load and database size remain unmeasured. With the bot enabled, booking, cancellation and coach participant actions trigger cards, selected alerts and refresh existing participant cards. Training edits, deletion and restoration update relevant cards and issue selected alerts; status messages and reminders are removed on time changes or deletion, and existing reminders are refreshed on a title/time edit. Separate booked/waitlist/rejected status messages now support preliminary expiry, scheduled final confirmation and cleanup, with mocked retry tests. Booking/cancellation fan-out, coach participant actions, deletion and edit/restoration are compared with Python; delivery ordering under concurrency still requires verification.
- Authenticated personal-data export includes the user's profile, bookings, sent messages, feedback and coach application. Confirmed account deletion checks coach roles and upcoming owned matches, atomically erases associated data and promotes waiting players, and clears the in-memory avatar cache. Match and training promotions trigger best-effort preview notices when the bot is enabled.
- Player/coach chat persistence, conversation listing and isolated threads are implemented. With the opt-in Telegram bot enabled, generic chat notifications respect preferences, omit message text, and are removed after expiry or reading. One chat-notification sequence is compared with Python.
- Feedback submissions are validated, rate-limited and saved; with the bot enabled, the owner receives the feedback text using the submitter's selected identity. Notification delivery is best-effort and has only been tested with mocked Telegram transport.
- Avatar proxy supports scoped tokens, current privacy checks, bounded in-memory caching, ETag and size limits. The reference disk cache is migrated: files live under `AVATAR_CACHE_DIR` (default `./data/cache/avatars`), writes are atomic, usage is capped at 200 MB with oldest-first cleanup to 80%, and account deletion removes the user's files. Real Telegram downloads still need end-to-end validation.
- Coach training creation, recurring batch creation, active listing, creator-only history and recycle bin, editing, deletion, restoration and purge are available. Batch creation skips duplicates and past dates and rolls back on storage failure. Participant listing, add, approve/reject, removal, restoration and reminder settings are available. Training tournament rooms are limited to active participants and managers; the creator can add or remove coach coauthors.
- Coach roster listing and manager-authorized addition/removal are available, including atomic removal of training coauthorship and owner-only manager-role changes. The owner or creator can transfer a training to a registered coach while preserving bookings. Applications can be submitted, viewed, approved or rejected with rate limiting and atomic decisions. With the bot enabled, best-effort notifications cover applications, decisions, added coaches and transfers; temporary notices and expired application cards are cleaned up. Application submission, new-coach and transfer notices are also compared with Python; delivery remains mock-tested and is not durable across failures or restart.
- Coaches can view other coaches' upcoming trainings and public coach details in the read-only club schedule; management permissions remain unchanged.
- The coach player directory supports notes, counts and Unicode-aware search while hiding anonymous players' real names. Authenticated training levels and coach biography endpoints are available. Search filtering runs in SQLite with the registered `search_norm` function and escaped `LIKE` patterns. A manual 50,000-player benchmark on the development machine measured about 80 ms for one match and 0.9 s for the full list including scoped-token generation; production latency and larger datasets remain unmeasured.
- Telegram HTTPS transport and training reminder tick are available behind the opt-in `SQASSIT_ENABLE_REMINDERS` switch. The tick persists successful deliveries, retries failures and deletes expired reminder and chat messages. It rechecks event and recipient state around each send: if settings or booking change during delivery, the stale message is scheduled for cleanup and is not counted for the new state. This is mock-tested and does not eliminate all concurrent-change or external-delivery races. Telegram delivery, concurrency and restart recovery remain unverified; this remains a preview. One due tick is also compared with the Python reminder in the contract test.
- A shared editable event-notification sender persists message IDs and expiry, and serializes simultaneous updates within one process. With the bot enabled, match creation, deletion, joining, leaving, approval, rejection and queue promotion trigger best-effort notifications with preference and anonymity checks. Match creation/deletion also updates opted-in users' match feeds; a periodic task refreshes or deletes existing feeds. Match creation, one leave/request notification sequence, feed publication and feed refresh are compared with Python; ordering under simultaneous events, restart recovery and real Telegram still need verification. Training notifications cover booking, cancellation, coach participant actions, edits, deletion and restoration. Expired match, training and match-feed cards are included in the opt-in bot/reminder cleanup loop.
- Core Telegram `/start`, `/phone`, `/slots`, self-contact, rules-message and slot/attendee callback handlers are implemented and tested in isolation. The coach-application callback is also implemented. On startup the opt-in bot refreshes existing pinned rules without sending new ones, covered with mocked success and failure tests. Polling and webhook are opt-in and covered with mocked tests, but have not been verified against Telegram. Before polling starts, webhook status is checked; an active webhook or unavailable Telegram causes startup to fail without modifying the webhook or dropping updates. Unrelated and malformed updates with an update ID are ignored and logged without payloads; transport and database failures remain retryable, and polling updates without an ID retain the offset. Retrying after a side effect can still cause duplicates. Slot booking and cancellation callbacks use the shared training notifier, including waitlist promotion, with mocked coverage. The callback is answered and the slot view refreshed before the best-effort fan-out, so slow Telegram notification requests do not delay the reply; real delivery, concurrency and restart recovery remain unverified. Remaining notification parity gaps are listed at the end of this file. An opt-in contract test compares the outgoing calls for these commands and callbacks with the Python bot.
- Experimental Axum HTTP shell renders the legacy templates and serves static files. Readiness checks SQLite with `SELECT 1` and the Telegram Bot API with `getMe`, caching the Telegram result for 60 seconds like the reference; it returns 503 with the reference Russian detail when either probe fails or no bot token is configured. The registered bot commands/callbacks and all 75 HTTP routes are ported, but real Telegram delivery remains unverified.

## Baseline and verification

On 2026-11-11 the Python reference tests ran in an isolated Python 3.12 environment: **299 passed, 2 skipped**, with coverage options disabled. The TestClient integration test stalled inside the sandbox and passed outside it. Rust unit tests and Clippy run through the root `Cargo.toml`; CI executes formatting, Clippy, tests, release build and a credential-free loopback smoke test of a staged binary and static files. The local optimized build and smoke test passed; this does not validate deployment, Telegram or a production data migration.

An opt-in Python/Rust contract test runs 147 scenarios covering profile onboarding, phone validation and normalization, notification settings, training booking/waitlist/cancellation, coach participant and training management, training archives, batch creation and purge, match and private-chat workflows, match participant decisions, the coach registry and manager roles, coach applications and decisions, coach profile editing, the read-only club schedule, training/match coauthors, training transfer, feedback, data export, public profile access by scoped token, avatar authorization and privacy, iCalendar export and confirmed account deletion. It also checks representative authorization denials for players, unauthenticated callers and non-manager coaches, validation failures, duplicate-training conflicts and feedback rate limiting. Static HTML pages are compared byte-for-byte. Responses are compared by HTTP status and JSON (or raw text/HTML) as well as selected columns from ten tables after the workflow. It suppresses Python Telegram tasks, checks message timestamps are near the test time and normalizes them, clock-dependent seconds, scoped tokens and the ICS timestamp. Registry and coauthor listings break equal timestamps by ID in Rust so ordering is deterministic; the test seeds the owner row one hour in the past to avoid second-boundary races. The local run passed outside the sandbox; CI is configured to run it with reference dependencies. Actual avatar file downloads, the Telegram webhook and real `getMe` remain outside this test, and event-notification calls are not compared.

A second opt-in Python/Rust test drives the same Telegram updates through both bot implementations and compares outgoing API methods and payloads: `/start`, `/phone`, `/slots`, fallback text, own and foreign contacts, slot and attendee callbacks, and coach-application approve/reject decisions, including an unauthorized and an already-decided callback. It also compares the resulting users, notification rows, coaches and applications. Bot defaults and empty callback-answer fields are normalized, and fake message IDs advance identically. Booking/cancellation callbacks are excluded because their notification fan-out is best-effort and mutates many messages.

A third opt-in test compares one due training-reminder tick: the reminder text and recipient call, `reminder_deliveries`, the stored `training_reminder` notification and the `reminder_sent` flag.

A fourth opt-in test compares expired-notification cleanup for training cards, chats, matches, match feeds, coach applications, notices, reminders and training-status messages, including the preliminary row that keeps its record after its message is deleted. It also checks that a transient deletion failure leaves the row for the next tick. Mixed-kind ordering is not compared because the Rust cleanup loops run concurrently.

A fifth opt-in test compares preliminary-to-final enrollment replacement: the final message text, the sent and deleted messages, and the updated notification row. It also covers a booked player with training notifications disabled, whose preliminary message and row are removed. The order of unrelated user calls is not compared.

A sixth opt-in test compares match notifications for an existing card: a player leaving, a new pending request, organizer deletion, request approval, waitlist promotion and rejection. It checks the management card and pending-application keyboard, booked-player updates, personal status text, edits of existing messages, notification rows and their expiry. Match feed refresh and removal on later ticks are compared separately.

A seventh opt-in test compares chat notifications: the first message sends an alert without the message body, a repeat edits the existing alert, the coach receives the reciprocal text, and a recipient with messages disabled receives nothing. Notification rows and their 24-hour expiry are checked.

An eighth opt-in test compares security and cache headers on the HTML pages, `/tabs`, health and unauthorized API responses, and static JavaScript/HTML: CSP, `nosniff`, referrer and permissions policies, cache lifetimes and content types. It caught and fixed a missing UTF-8 charset on static files.

A ninth opt-in test compares training-deletion notifications: booked/waitlist/rejected/reminder messages are deleted, the organizer card is edited without a pending-application button, and booked/waitlist/pending players receive the cancelled text. It caught and fixed delete ordering and a stray pending button on deleted trainings; it also aligned participant ordering with Python.

A tenth opt-in test compares coach-application notifications: the owner and managers with message notifications enabled receive an anonymous-applicant card with the applications button, while disabled managers get nothing. Notification rows and their 24-hour expiry are checked.

An eleventh opt-in test compares role notices: a new coach gets the coach-access message with the Web App button, a transferred training notifies the new coach only when training notifications are enabled, and a rejected applicant gets the rejection text. The notice rows and their 24-hour expiry are checked.

A twelfth opt-in test compares training edits and restoration: a title-only edit updates organizer, participant, booked, waitlist and reminder cards and sends change notices; moving a training deletes status messages and recreates them; restoring edits old cards back and recreates the booked confirmation. Python repeats identical no-op edits and alerts managers about the acting player on every edit; the comparison drops those duplicates and alerts, matching Rust's changed-text-only edits and silent card updates.

A thirteenth opt-in test compares booking and cancellation notifications: two bookings fill the capacity, later bookings join the waitlist, a disabled player's waitlist entry stays silent, a booked player cancels, and the first waitlisted player is promoted. It checks personal and organizer cards, status messages, manager alerts, reminder updates and final rows. Python's repeated no-op edits are dropped; manager alerts are part of the compared behavior.

A fourteenth opt-in test compares coach participant actions: approving a pending request, rejecting another, removing a booked player with FIFO promotion and restoring the removed player to the waitlist. It checks the player's personal card and short cancellation push, organizer cards and manager alerts. It caught and fixed the cancellation push using the full card text instead of Python's short status text.

A fifteenth opt-in test compares match creation and feed publication: the creator and coauthor receive organizer cards, booked players receive the updated roster, and opted-in users receive the upcoming-match feed while the creator, players who disabled match notifications and disabled users are skipped. A second upcoming match is listed in start order.

A sixteenth opt-in test compares match-feed refresh: a stale feed is edited, an unchanged feed is left alone, a disabled recipient's feed is deleted, and once all matches are past the remaining feeds are removed.

A seventeenth opt-in test compares `search_norm` with Python across every Unicode scalar value plus curated vectors for Cyrillic `ё`, German `ß`, Greek sigma, Turkish dotted/dotless i, ligatures, fullwidth forms, combining marks and emoji. It found 129 codepoints added after Unicode 9.0 that the bundled `unicode-casefold 0.2` tables did not fold; Rust now applies those mappings explicitly and the exhaustive comparison passes. It also checks the registered SQLite function for `NULL` and folded text.

Another opt-in test requests every one of the reference's 75 HTTP routes four times: without initData and as a player, a non-manager coach and the manager owner, each role against a fresh database. It reads the route decorators and derives a minimal valid JSON body from the Python OpenAPI schema, so the comparison reaches authorization instead of failing in body parsing. Responses are compared by status and JSON body across all 300 route/role pairs after normalizing clock-derived and per-session values; the only excluded bodies are FastAPI's pydantic error arrays for malformed request bodies, where Rust keeps its own validation wording. Every protected route returns the same 401 detail, player denials, coach 404s on foreign entities, manager 422s on invalid references and all domain error and success payloads match Python. A route missing from the Rust router, a role that authorizes differently or a divergent payload would surface immediately.

Another cross-language test compares new and synthetic old databases after migration: table columns, index metadata and columns, selected data/backfills, and a repeated Rust migration. It does not replace testing against an anonymized copy of the actual production database or a backup/restore rehearsal.

## Still required

This is **not yet a verified replacement**. All 75 reference HTTP routes are wired and the existing templates/static assets are served, but remaining release gates are:

- Cross-implementation parity does not cover actual avatar file downloads, the Telegram webhook or real `getMe`, and it normalizes time, scoped tokens and bot defaults; every route/role pair is compared by status and body for all roles, except FastAPI's pydantic error arrays for malformed bodies, and mixed-kind cleanup ordering is not compared; the training edit comparison normalizes Python's repeated no-op edits and edit-time manager alerts.
- Real Telegram polling, webhook registration, notifications, reminders and restart/concurrency behavior remain unverified; delivery is best-effort and can duplicate after a side effect fails.
- A local Chromium run with signed dev init data rendered the player page, schedule and profile, completed booking and cancellation, and loaded the match and coach pages; Telegram WebView-specific behavior, real avatar files, ICS and CSP still need end-to-end checks with a test bot. Synthetic local benchmarks cover 50,000-player search and a 2,000-training/12,000-booking schedule, but there is no production load or database-size measurement.
- A local smoke test rehearses an online SQLite backup and a restart from the copy with a signed-in profile marker. A rollback rehearsal lets the Python reference open the Rust-migrated database, read and overwrite the marker and add a training, after which Rust reads both changes back. Deployment on the target platform has not been rehearsed, and the Xray/VLESS scripts remain Python-only.

Do not deploy this crate in place of the Python application.
