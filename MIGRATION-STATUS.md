# Migration status

Reference: SQASSIT `736a779f59d9e13d7e3a0f0401d6dd1c642cfada`, imported under `legacy/`.

## Implemented in Rust

- Telegram Mini App initData and scoped token validation, with fixed vectors generated by the reference implementation.
- Stable anonymous identities and an in-memory sliding-window rate limiter.
- SQLite schema initialization and legacy column migrations, including notification expiry and onboarding backfills. SQLite uses WAL, a busy timeout, foreign keys, and the `search_norm` function.
- Atomic training booking, approval, rejection, cancellation and FIFO promotion, including simultaneous requests for the last place.
- Match creation and privacy-aware listing are available; creation atomically enrolls the organizer. Match attendance endpoints implement authenticated joining, leaving, approval and rejection with manager/coauthor checks, phone cutoff, rate limits and atomic FIFO promotion, including concurrent requests for the last place. Tournament room access is restricted to booked players and managers; only the organizer can delete a match or modify coauthors. As in the Python API, the coauthor list discloses their real identity to authenticated users; this behavior needs a privacy review. Match event notifications remain incomplete.
- Authenticated profile read/edit, privacy-aware public player profiles, iCalendar export, onboarding acknowledgement, notification settings, the player-facing training schedule, booking and cancellation use SQLite and Telegram initData. The schedule preserves anonymous participant rendering and local-time conversion. Booking and cancellation do not yet deliver Telegram notifications.
- Player/coach chat persistence, conversation listing and isolated threads are implemented. With the opt-in Telegram bot enabled, generic chat notifications respect preferences, omit message text, and are removed after expiry or reading.
- Avatar proxy supports scoped tokens, current privacy checks, bounded in-memory caching, ETag and size limits. Persistent disk cache is not migrated; real Telegram downloads still need end-to-end validation.
- Coach training creation, recurring batch creation, active listing, creator-only history and recycle bin, editing, deletion, restoration and purge are available; notifications for training changes are not yet delivered. Batch creation skips duplicates and past dates and rolls back on storage failure. Participant listing, add, approve/reject, removal, restoration and reminder settings are available. Training tournament rooms are limited to active participants and managers; the creator can add or remove coach coauthors.
- Telegram HTTPS transport and training reminder tick are available behind the opt-in `SQASSIT_ENABLE_REMINDERS` switch. The tick persists successful deliveries, retries failures and deletes expired reminder and chat messages. Other event notifications and the rest of the bot are not yet implemented; this remains a preview.
- A shared editable event-notification sender persists message IDs and expiry, and serializes simultaneous updates within one process. With the bot enabled, match creation, deletion, joining, leaving, approval, rejection and queue promotion trigger best-effort notifications with preference and anonymity checks. Match creation/deletion also updates opted-in users' match feeds; a periodic task refreshes or deletes existing feeds. This is mock-tested only: ordering under simultaneous events, restart recovery and real Telegram still need verification. Training events are not yet wired. Expired match and match-feed notifications are included in the opt-in bot/reminder cleanup loop.
- Core Telegram `/start`, `/phone`, `/slots`, self-contact, rules-message and slot/attendee callback handlers are implemented and tested in isolation. The coach-application callback is also implemented. Polling and webhook are opt-in and covered with mocked tests, but have not been verified against Telegram; unknown updates halt polling or receive a retryable webhook response. Event notifications remain incomplete. Slot changes do not yet send event notifications.
- Experimental Axum HTTP shell renders the legacy templates and serves static files. Readiness deliberately returns 503 while the API and bot are incomplete.

## Baseline and verification

On 2026-11-11 the Python reference tests ran in an isolated Python 3.12 environment: **299 passed, 2 skipped**, with coverage options disabled. The TestClient integration test stalled inside the sandbox and passed outside it. Rust unit tests and Clippy run through the root `Cargo.toml`; CI executes formatting, Clippy and tests.

## Still required

This is **not a runnable Rust replacement** yet. HTTP routes/templates, the rest of the data access and business logic, bot, notifications/scheduler, operational integration, cross-implementation contract tests and deployment/rollback validation remain to be implemented. Do not deploy this crate in place of the Python application.
